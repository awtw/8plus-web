一段首頁動畫可以很流暢，卻仍然讓人看不懂你在做什麼。設計動效之前，值得先寫下一句話：這個畫面要幫訪客理解哪件事？

如果答案只是「有科技感」，動畫很容易和其他網站交換使用。若能具體說出「把模糊需求整理成可驗證的系統」，畫面就有了屬於這個品牌的內容。

## 先有故事，再選技術

以工程服務為例，畫面可以從一張不完整的需求卡開始，逐步補上資料、權限與驗收條件，最後連到可操作的成果。訪客即使不知道 RAG 或部署工具，也能理解你如何工作。

這段故事不需要很多節點。每一步只帶出一個新資訊，並讓畫面中的狀態有原因。資料整理好了，才進入下一步；交付物出現後，就讓人可以查看案例。

HTML、SVG 或 CSS 往往就能表達這種過程。只有當空間、材質或大量物件確實有助於溝通時，再評估更複雜的圖形技術。

## 文字和按鈕不用等動畫

訪客可能已經知道自己需要什麼，也可能正在手機上快速查看。主標題、服務說明與主要按鈕應從一開始就能使用，不需要先看完片頭。

動畫結束後也要留下可閱讀的內容。把重要資訊放在 HTML 文字中，而不是只畫在 Canvas；讓畫面停下來之後，流程仍然成立。

## 控制權是設計的一部分

依 [W3C 對暫停、停止與隱藏的說明](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)，自動開始、持續超過五秒且與其他內容並列的非必要動態，需讓使用者能暫停、停止或隱藏。這不只是替特定少數人加的選項，也能幫助任何需要專心閱讀的人。

一種簡單做法，是短暫入場後停止，想看的人可以自己重播。偏好減少動態的訪客直接看到靜態版本。滑鼠懸停提供的資訊，也要讓鍵盤與觸控使用者取得。

## 手機需要重新編排

桌面能同時容納文案與圖形，手機不一定能。把複雜場景縮小，可能只會得到一堆看不清楚的標籤。

可以改成上方文案與按鈕、下方簡化流程。使用者不必拖曳、長按或精準碰到小節點才能理解主題。背景效果應保持安靜，避免和文字爭奪注意力。

## 用理解與體驗驗證效果

[Google Web Vitals](https://web.dev/articles/vitals) 以 LCP、INP 與 CLS 衡量載入、互動及穩定性；良好門檻分別為 2.5 秒、200 毫秒與 0.1，需觀察真實造訪的第 75 百分位。這些指標可以幫助檢查動畫是否拖累體驗，但不會直接告訴你內容是否有說服力。

所以還要請目標訪客說出：這個人能幫我做什麼？我想合作時下一步在哪裡？如果畫面很吸睛，卻讓這兩題更難回答，就該調整資訊與動效的關係。

好的首頁動畫應該留下理解。當畫面停止，訪客仍知道自己為什麼要繼續看你的作品。
